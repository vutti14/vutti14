## 1. ปัญหาที่ระบบนี้แก้

บริษัทจ่ายเงินหน้างานเดือนละราว 2.5 ล้านบาท ผ่านใบเบิกราว 240 ใบ กระจาย 15 โครงการ 72 อาคาร โดยผ่านไลน์และ Google Sheets

ผลที่เกิดขึ้นจริงจากการวิเคราะห์ข้อมูล 6 เดือน:

| ปัญหา | หลักฐานจากข้อมูลจริง |
|---|---|
| แยกค่าของกับค่าแรงไม่ได้ | ค่าแรงที่ระบุชัดมีแค่ 8.4% ทั้งที่ควรเป็น 26-28% |
| ภาษีหัก ณ ที่จ่ายตกหล่น | ประมาณ 68,000 บาทใน 6 เดือน |
| เทียบราคาข้ามร้านไม่ได้ | 269 รายการจาก 41 ร้าน แต่ชื่อตรงกันข้ามร้านแค่ 2 รายการ |
| ตรวจรายการซ้ำไม่ได้ | 12 กลุ่ม 237,528 บาท ที่ไม่มีใครเคยเห็น |

| ไม่รู้ว่าอาคารไหนทำไปกี่ % | มีอาคารเดียวที่ตอบได้ คือ Satoshi L ทำไป 36.1% เหลือ 1,807,072 บาท |
| งานอนุมัติกระจุกเกินไป | 58% ของใบเป็นเงินแค่ 10.1% |

## 2. หลักการออกแบบ 10 ข้อ

หลักเหล่านี้มาจากบทเรียนที่เจอระหว่างวิเคราะห์ข้อมูลจริง ไม่ใช่ทฤษฎี **ห้ามละเมิดโดยไม่ได้รับอนุมัติจากเจ้าของระบบ**

1. **ห้ามพิมพ์รหัสเอง** — ทุกรหัส (โครงการ อาคาร หมวดงาน vendor) เป็น dropdown เท่านั้น *(เหตุผล: `WAl` vs `WAL`)*
2. **ห้ามลบ ห้ามแก้ยอดที่จ่ายแล้ว** — การเปลี่ยนแปลงทุกอย่างเกิดจากใบใหม่ที่อ้างใบเดิม
3. **รหัสสั้น ไม่แบกความหมาย** — คุณสมบัติเก็บเป็นคอลัมน์ ไม่เก็บในรหัส *(เหตุผล: รหัส 10 หลักเดิมรองรับผู้เบิกได้ 10 คน แต่มี 11 คน)*
4. **ทุกค่าต้องรู้ที่มา** — ทุกตารางมีฟิลด์ `ที่มาของค่า`: ข้อเท็จจริง / อนุมาน / นำเข้าย้อนหลัง
5. **เพิ่มแกน ไม่เพิ่มโค้ด** — อยากได้รายละเอียดมากขึ้นให้เพิ่มมิติ ไม่ใช่เพิ่มรหัส
6. **เทียบต้นทุนได้เฉพาะ `design_code` เดียวกัน** — ห้ามเทียบข้ามแบบอาคาร
7. **วันเริ่มสร้าง = วันที่เบิกใบแรก** — คำนวณอัตโนมัติ ไม่ให้คนกรอก
8. **แสดงเป็นยอดเงิน ไม่ใช่จำนวนใบ** — "ภาษีซื้อขอคืนไม่ได้ 186,000 บาท" ทำให้คนวิ่งตาม แต่ "ค้าง 47 ใบ" ไม่
9. **ตรวจรายการซ้ำที่ระดับอาคาร ไม่ใช่ระดับโครงการ** — *(เหตุผล: กลุ่มขึ้นอาคารทีละคู่ ค่าใช้จ่ายหารสองเท่ากันเป็นเรื่องปกติ ถ้าตั้งผิดระดับจะเตือนผิด 65%)*
10. **มือถือมาก่อน** — หน้าขอเบิกและหน้าอนุมัติต้องใช้บนมือถือด้วยมือเดียวได้

## 3. ผู้ใช้และสิทธิ์

| บทบาท | คน | ทำอะไรได้ |

| **VIEWER** | อิม (I) | ดูอย่างเดียว |

### 3.2 การเข้าสู่ระบบ

- `username` = อีเมล (มีครบ 11 คนใน `05_DIM_PERSON`)
- รหัสผ่านครั้งแรก = เบอร์โทร **บังคับเปลี่ยนทันทีที่ล็อกอินครั้งแรก**
- **ห้ามเก็บรหัสผ่านจริงในฐานข้อมูล** เก็บเฉพาะ bcrypt hash
- **บังคับ 2FA สำหรับ A, K, S** (สามบัญชีที่ทำให้เงินออกจากบริษัทได้)
- ผูกบัญชีไลน์ครั้งแรกเพื่อใช้อนุมัติผ่านไลน์

### 3.3 กฎสิทธิ์เฉพาะ

- PM เห็นเฉพาะโครงการที่ตัวเองรับผิดชอบ (CEO/COO/FINANCE/ACCOUNT เห็นทั้งหมด)
- **คนสร้าง vendor กับคนยืนยัน vendor ต้องไม่ใช่คนเดียวกัน**
- COO อนุมัติใบของตัวเองได้ (เจ้าของระบบยืนยันแล้ว) แต่ระบบต้องขึ้นป้าย "ใบของผู้อนุมัติเอง" และนับแยกในรายงาน

## 4. วงจรสถานะใบเบิก

```
ร่าง ──► รออนุมัติ ──► อนุมัติแล้ว ──► จ่ายแล้ว ──► ปิดรายการ
  │           │              │              │
  │           │              │              └──► มีใบกลับรายการ
  │           │              └──► ยกเลิก (COO เท่านั้น)
  │           └──► ไม่อนุมัติ / ยกเลิก (ผู้ขอเอง)
  └──► ลบได้ (ยังไม่ส่ง)
```

**"ปิดรายการ"** = จ่ายแล้ว + ของมาครบ + เอกสารครบตามประเภท (ดูข้อ 7)

**กฎ:** ยอดเงินในใบที่สถานะ `จ่ายแล้ว` ขึ้นไป **แก้ไม่ได้ตลอดกาล** แก้ได้เฉพาะข้อมูลประกอบ (หมวดงาน อาคาร หมายเหตุ) และทุกการแก้บันทึกลง `audit_log`

## 6. กฎตรวจสอบ (Validation)

### 6.1 กฎบล็อก — ผ่านไม่ได้

| # | กฎ | ข้อความ |

## 7. เอกสารที่ต้องครบตามประเภท

**บริบท:** บริษัทมักโอนเงินก่อนเพื่อให้ของมาเร็ว → ของตามมา → ใบเสร็จตามมา → **ใบกำกับภาษีมาช้าที่สุด**

### ค่าของ — 3 ช่องแยกกัน

| ช่อง | ใครติ๊ก | ตอบคำถาม |
|---|---|---|
| **ของมาแล้ว** (ใบส่งของ) | PM | จ่ายไปแล้วได้ของหรือยัง |
| **ใบเสร็จรับเงิน** | บัญชี | ร้านออกใบให้หรือยัง |
| **ใบกำกับภาษี** | บัญชี | ขอคืนภาษีซื้อได้หรือยัง |

### ค่าแรง — 3 ช่องแยกกัน

| ช่อง | ใครติ๊ก |
|---|---|
| **ใบสำคัญรับเงิน / ใบเสร็จ** | บัญชี |
| **หัก ณ ที่จ่ายแล้ว** + ยอดที่หัก | บัญชี |
| **ออกหนังสือรับรองแล้ว** + เลขที่ | บัญชี |

**ใบจะ "ปิดรายการ" ได้เมื่อครบทุกช่องตามประเภทเท่านั้น**

**สำคัญที่สุดในทางภาษี:** เก็บทั้ง *เดือนที่จ่ายเงิน* และ *เดือนบนใบกำกับภาษี* แยกกัน เพราะภาษีซื้อใช้ตามเดือนของใบกำกับ **ถ้าเก็บวันเดียว บัญชีจะยื่น ภ.พ.30 ผิดเดือนทั้งปี**
