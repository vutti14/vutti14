ตรวจจาก Verisign RDAP ซึ่งเป็นทะเบียนกลางของ .com โดยตรง ไม่ใช่ตัวกลาง

### ทำไมเรื่องนี้ด่วนกว่าทุกเรื่อง

- **โดเมนกับโฮสต์เป็นบิลแยกกัน** โดเมนจดที่ PublicDomainRegistry แต่เว็บอยู่บน LnwShop
  การที่คุณจ่าย LnwShop อยู่ **ไม่ได้** แปลว่าโดเมนต่ออายุให้อัตโนมัติ
  นี่คือสาเหตุที่เว็บธุรกิจเล็กหายไปจากอินเทอร์เน็ตบ่อยที่สุด — ไม่ใช่ถูกแฮ็ก แต่ลืมต่อโดเมน
- **โดเมนอายุ 13 ปีซื้อคืนไม่ได้** ความน่าเชื่อถือที่ Google สะสมให้โดเมนมา 13 ปี
  คือทรัพย์สินที่เงินซื้อไม่ได้ ถ้าปล่อยหลุดแล้วไปจดใหม่ ก็เริ่มจากศูนย์
- **โดเมน .com เชิงพาณิชย์ที่หลุดมีคนดักซื้อ** มีบอทเฝ้ารายการโดเมนหมดอายุ
  โดเมนที่มีคำค้นภาษาไทยชัดเจนและมีประวัติการค้าถูกดักซื้อแล้วตั้งราคาขายคืน
  หรือเอาไปทำเว็บพนัน ซึ่งจะพาลิงก์เก่าทั้งหมดของคุณไปด้วย
- **ของทุกอย่างพังพร้อมกัน** ถ้าโดเมนหลุด: เว็บดับ, ลิงก์ในนามบัตรและใบเสนอราคาดับ,
  ลิงก์ที่ผมทำเชื่อมสองเว็บดับ, งาน SEO ทุกชิ้นในโปรเจกต์นี้เป็นศูนย์

1. เข้า PublicDomainRegistry (หรือตัวแทนที่คุณซื้อผ่าน — ถ้าจำไม่ได้ให้ดูอีเมลเก่า
   ค้นคำว่า "silalang.com renewal" หรือ "domain expiry")

3. **เปิด auto-renew** และเช็กว่าบัตรที่ผูกไว้ยังไม่หมดอายุ
4. เช็กว่าอีเมลที่ผูกกับโดเมนเป็นอีเมลที่คุณยังเปิดอ่านอยู่จริง

## 2. หน้าแรกหนัก 12–17 MB — ลูกค้ามือถือรอ 28–55 วินาที

### ตัวเลขที่วัดได้

เกณฑ์ที่ Google ถือว่า "ผ่าน": LCP ต่ำกว่า 2.5 วิ · CLS ต่ำกว่า 0.1

### อ่านตารางนี้ยังไง

**ปัญหาอยู่ที่หน้าแรกเป็นหลัก ไม่ได้พังทั้งเว็บ** หน้าสินค้าได้ 61–63 ซึ่งไม่ดีแต่พอใช้
หน้าแรกได้ 19 กับ 27 ซึ่งคือพัง นี่เป็นข่าวดี เพราะแปลว่าแก้จุดเดียวได้ผลเยอะ
ไม่ต้องรื้อ 330 หน้า

**LCP 55 วินาที หมายความว่าอะไร** LCP คือเวลาที่รูปหรือข้อความใหญ่สุดบนจอโหลดเสร็จ
55 วินาทีคือลูกค้าเปิดเว็บคุณบนมือถือ เห็นหน้าขาวหรือหน้าโหลดไม่เสร็จ แล้วกดปิด
งานวิจัยของ Google บอกว่าเกิน 3 วินาที คนออกไปแล้วเกินครึ่ง
ที่ 55 วินาที คนที่รอจนจบคือคนที่ตั้งใจมาหาคุณอยู่แล้วเท่านั้น

**ตัวการชัดเจน: รูป** เครื่องมือบอกตรง ๆ ว่าถ้าจัดการรูปให้ถูก
จะประหยัดได้ **15.65 วินาที** (หินอ่อน.com) และ **13.35 วินาที** (silalang.com)
ไม่มีรายการอื่นในผลตรวจที่ใกล้เคียงเลข 2 หลักนี้เลย — อันดับสองคือ JavaScript ที่ 2.7–3.45 วินาที

### สาเหตุที่น่าจะเป็น และวิธีแก้

หน้าแรก LnwShop หนักจากรูปแบนเนอร์สไลด์ที่อัปโหลดผ่านหลังร้าน
คนส่วนใหญ่อัปรูปจากกล้องหรือมือถือตรง ๆ ซึ่งไฟล์ละ 3–5 MB
และ LnwShop เอาไปแสดงตามขนาดไฟล์เดิม ไม่ได้ย่อให้

**วิธีแก้ ทำในหลังร้านได้เลย ไม่ต้องแก้โค้ด**

1. ดาวน์โหลดรูปแบนเนอร์หน้าแรกทั้งหมดที่ใช้อยู่เก็บไว้ก่อน
2. ย่อรูปให้**กว้างไม่เกิน 1600 px** (จอมือถือกว้างจริงแค่ 360–430 px
   แบนเนอร์ 4000 px ไม่ได้ทำให้สวยขึ้นเลยบนมือถือ)
3. บีบอัดให้**ไฟล์ละไม่เกิน 200 KB** ใช้ squoosh.app หรือ tinypng.com ฟรี ไม่ต้องลงโปรแกรม
   ถ้าเลือก format ได้ ให้เลือก **WebP** เล็กกว่า JPEG ประมาณ 30% ที่ความชัดเท่ากัน
4. ลบรูปเดิมในสไลด์ แล้วอัปรูปใหม่แทน
5. **ลดจำนวนสไลด์ลงเหลือ 3–4 รูป** ถ้าตอนนี้มี 8–10 รูป
   ลูกค้าแทบไม่เคยดูเกินรูปที่สาม แต่เบราว์เซอร์โหลดทุกรูป

**เป้าที่ควรได้:** หน้าแรกจาก 12–17 MB ลงมาต่ำกว่า 2 MB
คะแนนควรขึ้นจาก 19–27 ไปที่ 55–70 โดยไม่ต้องแตะอะไรอย่างอื่นเลย

6. ทำเสร็จแล้วบอกผม ผมรันวัดซ้ำให้ทันที จะได้เห็นตัวเลขก่อน–หลังจริง ไม่ใช่เดา

## 3. หน้าเว็บกระตุกตอนโหลด (CLS 0.375 และ 0.506)

CLS วัดว่าหน้าเว็บขยับไปมาแค่ไหนตอนโหลด เกณฑ์ผ่านคือต่ำกว่า 0.1
silalang.com ได้ 0.506 คือเกินเกณฑ์ 5 เท่า

อาการที่ลูกค้าเจอ: กำลังจะกดปุ่ม "สั่งซื้อ" รูปโหลดเสร็จ หน้าดันลงมา กดโดนอย่างอื่น

สาเหตุที่เครื่องมือระบุ: `unsized-images` — รูปไม่ได้บอกความสูงความกว้างไว้ล่วงหน้า
เบราว์เซอร์เลยไม่รู้จะเว้นที่ไว้เท่าไร พอรูปมาถึงก็ดันของที่อยู่ข้างล่างลงไป

ผมเขียน CSS แก้ให้แล้วในส่วน `[11]` ของทั้ง `patch/custom.css` และ
`patch-silalang/custom.css` วิธีใช้เหมือนเดิม — ก๊อปไปวางในหลังร้าน
ตรงช่องใส่ CSS เพิ่มเติม ใช้เวลา 5 นาที ไม่ต้องรอข้อ 2

## 4. สิ่งที่พบเพิ่ม และสิ่งที่พิสูจน์ว่าผมคิดผิด

### แชร์ลิงก์ใน LINE หรือ Facebook ไม่ขึ้นรูปตัวอย่าง

ผมลองดึง preview ของหน้าแรกและหน้าเกี่ยวกับเรา ทั้งสองเว็บ รวม 4 URL
**ทั้ง 4 timeout ทั้งหมด** ลองซ้ำก็ timeout เหมือนเดิม

แปลว่าเวลาคุณหรือลูกค้าแชร์ลิงก์เว็บคุณใน LINE / Facebook
ตัวดึงข้อมูลของแพลตฟอร์มรอไม่ไหวแล้วเลิกดึง ผลคือการ์ดตัวอย่างไม่ขึ้น
เหลือแต่ลิงก์เปล่า ๆ ที่ไม่มีใครอยากกด

สำหรับธุรกิจไทยที่ปิดการขายผ่าน LINE เป็นหลัก นี่คือความเสียหายที่จับต้องได้
และ**แก้ได้ด้วยข้อ 2 ข้อเดียว** — ไม่ต้องทำอะไรเพิ่ม
หน้าเบาลงแล้วตัวดึง preview จะทำงานทันเอง

### ไม่มีข้อมูลผู้ใช้จริงใน Chrome UX Report เลย

ผมขอข้อมูล Core Web Vitals จากผู้ใช้ Chrome จริงย้อนหลัง 6 เดือน
ได้คำตอบกลับมาว่า *"not enough Chrome traffic for real-user data"* ทั้งสองโดเมน

เกณฑ์ขั้นต่ำของ CrUX คือต้องมีผู้ใช้ Chrome ระดับหลักร้อยคนต่อหน้าต่าง 28 วัน
การที่ทั้งสองเว็บไม่ติดเกณฑ์ หมายความว่าทราฟฟิกจริงต่ำกว่านั้น

**เรื่องนี้ทำให้ผมต้องถอนสมมุติฐานของตัวเองข้อหนึ่ง**

ผมเสนอไว้ว่า "พอเปิดสิทธิ์ GA4 แล้วจะจัดลำดับ 330 หน้าใหม่ตามทราฟฟิกจริง"
และพูดเหมือนว่านั่นคือกุญแจที่ปลดล็อกทุกอย่าง ตอนนี้ผมคิดว่าผมขายไอเดียนั้นเกินจริง
ถ้าทราฟฟิกน้อยขนาดไม่ติดเกณฑ์ CrUX ตัวเลข GA4 รายหน้าจะเล็กและแกว่งมาก
การเอา 330 หน้ามาเรียงตามยอดวิวที่ต่างกันหน้าละ 2–3 ครั้งไม่ใช่การวิเคราะห์ มันคือการดูเลขสุ่ม

ผมยังอยากได้สิทธิ์ GA4 อยู่ แต่เหตุผลเปลี่ยนไป —
ไม่ใช่เพื่อจัดลำดับ 330 หน้า แต่เพื่อตอบคำถามพื้นฐานกว่านั้น:
คนเข้ามาจากช่องทางไหน, เข้ามาแล้วอยู่ต่อหรือออกเลย, มีใครกดโทรหรือกด LINE ไหม
สี่ข้อนี้ต้องการตัวเลขหยาบ ๆ ก็ตอบได้ ไม่ต้องการความละเอียดรายหน้า

### เรื่องที่ยังดีอยู่

- SEO score 92/100 ทุกหน้าที่วัด — โครงสร้างพื้นฐานไม่มีปัญหา
- Best practices 96–100/100 — ไม่มีช่องโหว่ความปลอดภัยที่เครื่องมือจับได้
- Web Risk ของ Google ไม่ขึ้นธงมัลแวร์หรือฟิชชิงทั้งสองโดเมน
- เวลาตอบจากเซิร์ฟเวอร์ LnwShop เร็ว (154 ms) — **ปัญหาไม่ได้อยู่ที่โฮสต์
  ไม่ต้องย้ายโฮสต์ และใครที่มาเสนอให้ย้ายเพราะ "เว็บช้า" คือเสนอผิดจุด**

### เรื่องที่ควรทำแต่ไม่ด่วน

- **Accessibility 53–77/100** รายการที่ซ้ำทุกหน้า: รูปไม่มี `alt`,
  ลิงก์ที่ไม่มีข้อความบอกว่าไปไหน, สีตัวอักษรกับพื้นหลังความต่างไม่พอ,
  ลำดับหัวข้อ H1→H2→H3 ข้ามขั้น
  `alt` มีผลกับ Google Images ด้วย ซึ่งสำคัญกับธุรกิจขายหินที่ลูกค้าค้นด้วยรูป
  ทำไปเรื่อย ๆ ตอนแก้สินค้าแต่ละตัวได้ ไม่ต้องรีบทำทีเดียว 330 หน้า
- Render-blocking 2.35–2.7 วินาที และ unused JavaScript — เป็นของที่ LnwShop
  ใส่มาให้ทุกร้าน เราแก้ไม่ได้ ไม่ต้องเสียเวลาคิด
- `font-display` (เสียไป 250–650 ms) — ผมเขียน CSS แก้ไว้รอบแรกแล้วลบออก
  เพราะมันแก้ไม่ได้จริงจากช่อง CSS เพิ่มเติม `font-display` ต้องใส่ใน
  `@font-face` ตัวเดิมที่ประกาศฟอนต์ ซึ่ง LnwShop เป็นคนประกาศ ไม่ใช่เรา
  เขียนทับจากข้างนอกไม่มีผล ผมไม่อยากแปะ CSS ที่ดูเหมือนทำงานแต่ไม่ทำอะไรให้คุณ
